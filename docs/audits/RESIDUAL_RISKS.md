# Residual risks (2026-10-20)

Status: CURRENT (final, wave F, 2026-10-20). It lists what remains after remediation and independent QA
verification ([LAUNCH_ACCEPTANCE.md](LAUNCH_ACCEPTANCE.md)), why it is accepted or left open, and who owns it.
None of these is a known exploitable vulnerability in the local build; the owner items block production. IDs refer to [FULL_RISK_REGISTER.md](FULL_RISK_REGISTER.md).

| OPS-10 (*2026-10-25, corrected 2026-10-26*) | After `REQUEST_TIMEOUT_SECONDS` a synchronous endpoint's thread keeps running. Only reads, retries and back-off are bounded by the request deadline: every write's first attempt still starts after it, with its full timeout (D1 15 s, KV 30 s), so the remaining work is a chain of single write attempts. A write refused with 429 after the deadline is not retried (that statement is lost), and a sequence with a read between two writes stops at the read (a scenario run cut off after storing its forecast leaves the scenario's last-run link and the usage event unwritten). The S3/R2 object store (boto3 retries) and MLflow tracking calls are not bounded at all | Refusing a write's first attempt left a report cut off at 30 s without any row and its files orphaned (review PLAT-B-01); with the first attempt allowed, such a report ends with a `failed` (or `succeeded`) row and audit rows land. Cutting a write short would make its outcome ambiguous. S3/R2 and online MLflow are not used on the request path of the zero-cost topology | Backend | Moving objects to R2, serving from an online MLflow, or a request route that approaches 30 s |
| GW-C2 (*2026-10-25, revised 2026-10-26*) | The gateway's stale public copy is labelled with the time it was last written: when its content last changed or, for unchanged content, the last daily refresh. The label can therefore be up to about a day older than the backend's last answer before the outage (longer if a refresh write failed, for example on an exhausted KV quota), and the copy is purged only by hand | Rewriting on every answer would spend the KV write quota (up to 288 writes a day for the snapshot); never rewriting unchanged content let the label name a time weeks before the outage (review PLAT-B-02). A daily refresh (`EDGE_CACHE_REFRESH_MS`) bounds the label's age at about 2 writes a day for both keys | Gateway | If visitors need the exact time of the last successful check (that would need a write per check or a second store) |
